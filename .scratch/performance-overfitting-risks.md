# Performance-ticket overfitting risks

Date: 2026-08-02. Scope: the open `bug` issues whose primary subject is a measured performance defect, excluding #127 because it prompted this review: [#106](https://github.com/skolldev/outpost/issues/106), [#128](https://github.com/skolldev/outpost/issues/128), [#130](https://github.com/skolldev/outpost/issues/130), [#131](https://github.com/skolldev/outpost/issues/131), [#132](https://github.com/skolldev/outpost/issues/132), and [#133](https://github.com/skolldev/outpost/issues/133). This is not a claim that the defects are unreal. It identifies where their ticket wording or acceptance tests reward a locally green result without proving the product-level trade.

`Explicit risk` means the ticket itself offers or requires the risky path. `Inferred risk` means the loophole comes from the repository around the ticket.

## Highest-risk gaps

1. **The retrieval harness still sends non-default request shapes for logs and traces.** The UI defaults the global range to 14 days and turns it into `from` ([`filters.ts:28-36`](../ui/src/app/core/filters.ts#L28-L36)); both pages send that value ([`logs.ts:90-114`](../ui/src/app/pages/logs/logs.ts#L90-L114), [`traces.ts:84-112`](../ui/src/app/pages/traces/traces.ts#L84-L112)). But the guard and benchmark call `/logs` and `/traces` with `from=null` ([`LogQueryPerformanceTest.java:195-206`](../server/src/test/java/dev/outpost/query/LogQueryPerformanceTest.java#L195-L206), [`RetrievalBenchmark.java:264-300`](../server/src/test/java/dev/outpost/bench/RetrievalBenchmark.java#L264-L300)). Unlike #126's imaginary shape, this one is reachable through the UI's “All time” option ([`shell.ts:67-75`](../ui/src/app/layout/shell.ts#L67-L75)), but it is not the default. The repository already records request-shape mismatch as the central lesson from #126 ([`measuring-retrieval.md:316-342`](../docs/performance/measuring-retrieval.md#L316-L342)). **Risk:** optimize the rare worst-case shape while never measuring the normal request or its common project/environment variants.

2. **The benchmark tier reports latency but does not gate it.** Its contract is correctness/run validity only; there is no wall-clock threshold ([`measuring-retrieval.md:9-25`](../docs/performance/measuring-retrieval.md#L9-L25)). That is sensible for CI, but “run the benchmark” is not by itself an acceptance condition. A change can satisfy a plan-shape assertion while remaining slow, or make an unasserted benchmark row worse.

3. **Every new telemetry index or rollup has a write and upgrade side.** `log_record`, `event`, and `txn` are partitioned append-heavy tables ([`V2__phase1_domain.sql:80-100`](../server/src/main/resources/db/migration/V2__phase1_domain.sql#L80-L100), [`V4__phase3_logs.sql:8-26`](../server/src/main/resources/db/migration/V4__phase3_logs.sql#L8-L26), [`V5__phase4_tracing.sql:12-31`](../server/src/main/resources/db/migration/V5__phase4_tracing.sql#L12-L31)). The retrieval tickets generally specify only read acceptance. #127 demonstrated why the missing ingest/backfill/retention acceptance matters.

## #128 — global log ordering

Ticket: [Log list: no index supports the global stream's ordering](https://github.com/skolldev/outpost/issues/128). The controller orders every list by `(timestamp, id)` descending ([`LogController.java:95-142`](../server/src/main/java/dev/outpost/query/LogController.java#L95-L142)); the disabled guard checks an unfiltered, unbounded page one for no `Sort` and `<1,000` logical-I/O blocks ([`LogQueryPerformanceTest.java:82-98`](../server/src/test/java/dev/outpost/query/LogQueryPerformanceTest.java#L82-L98)).

- **Inferred risk — benchmark the All-time/global request, then call it the log page.** The real default includes `from=14d`, and users may select one or several projects and environments. The proposed global `(timestamp, id)` index can make the ticket guard green while a selective environment or multi-project request walks that index and filters a large fraction of rows. The API and ADR explicitly support repeated project/environment filters ([`LogController.java:49-61`](../server/src/main/java/dev/outpost/query/LogController.java#L49-L61), [`0009-multiselect-project-filter.md:1-3`](../docs/adr/0009-multiselect-project-filter.md#L1-L3)). Acceptance covers none of those shapes.
- **Inferred risk — stop at page one.** The only #128 acceptance test is page one. The existing deep-page check compares page N with whatever page one costs, so two equally bad full scans pass together ([`LogQueryPerformanceTest.java:100-110`](../server/src/test/java/dev/outpost/query/LogQueryPerformanceTest.java#L100-L110)). The new index should be verified against a walked cursor under the same UI-shaped filters, not inferred from page one.
- **Inferred risk — buy the read with unmeasured log writes.** The fix adds another index entry for every log record and creates/builds that index across all existing weekly partitions. Log ingestion is already the signal whose throughput collapses under large batches; the write path is one batch insert after origin upserts ([`LogStore.java:52-89`](../server/src/main/java/dev/outpost/pipeline/LogStore.java#L52-L89)). Neither issue acceptance nor the disabled guard asks for an ingest before/after, index-size estimate, or blocking migration note.
- **Acceptance hardening:** measure default 14d and All time, each global plus project/environment shapes; walk a deep cursor; name the intended index in the plan where meaningful; record `logEnvelopeStepLoad` before/after and migration build time/size.

## #130 — correlated release issue counts

Ticket: [Release list runs a correlated unbounded count over event per row](https://github.com/skolldev/outpost/issues/130). The UI makes a single-project request and renders `issue_count` ([`releases.ts:29-37`](../ui/src/app/pages/releases/releases.ts#L29-L37), [`releases.html:24-63`](../ui/src/app/pages/releases/releases.html#L24-L63)). The controller's correlated `count(DISTINCT issue_id)` is at [`ReleaseController.java:50-64`](../server/src/main/java/dev/outpost/query/ReleaseController.java#L50-L64). Acceptance only requires total query I/O below two full scans of the entire `event` table ([`ReleaseQueryPerformanceTest.java:35-66`](../server/src/test/java/dev/outpost/query/ReleaseQueryPerformanceTest.java#L35-L66)).

- **Explicit risk — certify an O(retention) query as fixed.** The ticket explicitly permits “compute the counts in one pass (`GROUP BY release`)”. That removes the per-release multiplier, but still scans/aggregates retained events on every releases-page load. It can pass at 1.99 full scans while preserving the repository's defining retrieval failure mode: request cost grows with the dataset ([`measuring-retrieval.md:3-7`](../docs/performance/measuring-retrieval.md#L3-L7)).
- **Inferred risk — the comparator is much broader than the request.** Guard data has two projects ([`TelemetrySeeder.java:77-83`](../server/src/test/java/dev/outpost/support/TelemetrySeeder.java#L77-L83)); the endpoint requests one, while `fullScanCost("event")` prices the whole installation. The test therefore permits a project-scoped page to read work proportional to unrelated projects.
- **Inferred risk — keep the correlation and tune for eight releases.** The guard seeds eight releases per project while the endpoint permits 200 rows ([`TelemetrySeeder.java:80-82`](../server/src/test/java/dev/outpost/support/TelemetrySeeder.java#L80-L82), [`ReleaseController.java:60-63`](../server/src/main/java/dev/outpost/query/ReleaseController.java#L60-L63)). A supporting event index could make eight correlated probes fit under the ceiling without removing the per-output-row structure that the ticket diagnoses.
- **Inferred risk — return fast wrong counts.** The performance test only explains the SQL. There is no server integration test asserting release issue-count values; the UI test supplies a mocked `issue_count` ([`releases.spec.ts:20-27`](../ui/src/app/pages/releases/releases.spec.ts#L20-L27)). A grouped join with duplicated rows, a stale rollup, or a retention/backfill error can pass acceptance.
- **Inferred risk — repeat #127 on the write path.** A rollup is also an explicit option, but acceptance says nothing about its data model, event-ingest maintenance, redelivery, retention rebuild, or migration backfill. Exact `DISTINCT issue_id` needs membership semantics, not a blindly incremented event counter.
- **Acceptance hardening:** require the event work to be independent of total retention (or explicitly accept one full scan and record benchmark latency); test 1 vs 200 release rows and multiple projects; assert exact counts across duplicate events and retention; if using a rollup/index, benchmark error ingest and document upgrade cost.

## #131 — users affected

Ticket: [Issue list: users-affected aggregate has no time bound](https://github.com/skolldev/outpost/issues/131). `attachAggregates` executes a separate unbounded distinct-user query for each 50-issue page ([`IssueController.java:169-178`](../server/src/main/java/dev/outpost/query/IssueController.java#L169-L178), [`IssueController.java:194-228`](../server/src/main/java/dev/outpost/query/IssueController.java#L194-L228)). Acceptance requires pruning from the fixed 14-day sparkline start and fitting below the sparkline ceiling ([`IssueQueryPerformanceTest.java:239-271`](../server/src/test/java/dev/outpost/query/IssueQueryPerformanceTest.java#L239-L271)).

- **Explicit risk — silently redefine the product metric.** The ticket suggests bounding the count to “the window the UI actually shows,” but the UI labels the users column simply “Users”; only the sparkline is labeled “Last 14d” ([`issues.html:47-54`](../ui/src/app/pages/issues/issues.html#L47-L54)). Adding the guard's fixed 14-day predicate changes lifetime users to 14-day users without an explicit product decision or label change.
- **Inferred risk — mismatch the selected range.** The list's global range can be 1h, 24h, 7d, 14d, 30d, or All time, and reaches the issue list as `from`; the users-affected guard instead hardcodes `sparklineSince()` (14 days). A green result can therefore display 14-day users beside a one-hour or all-time-filtered list.
- **Inferred risk — prove pruning, not correctness.** An empty or rollup-backed event scan trivially satisfies `partitionsScanned(event) ⊆ allowed`, and the endpoint integration test only checks that the `users_affected` key exists, not its value ([`IssuePaginationIntegrationTest.java:118-125`](../server/src/test/java/dev/outpost/query/IssuePaginationIntegrationTest.java#L118-L125)). A stale/zero/wrong-window result can pass the named acceptance test.
- **Explicit risk — underestimate an exact-distinct rollup.** The ticket offers a rollup “like `issue_env_stats`”, but distinct users are not additive: the same user appearing on several days must count once. An exact time-window rollup needs issue/user membership with expiry (and retention/privacy behavior), potentially far higher cardinality and write cost than the three-row-per-issue environment rollup. None of that is in acceptance.
- **Acceptance hardening:** first specify whether the value is lifetime, fixed 14d, or selected-range; label it in the UI; assert exact values at both sides of the boundary, repeat users across days, null users, each range option, redelivery, and retention. If rollup-backed, benchmark error ingest and assert recompute equivalence.

## #132 — log attribute equality

Ticket: [Log attribute equality cannot use the attributes GIN index](https://github.com/skolldev/outpost/issues/132). The current SQL uses text extraction (`attributes->>? = ?`) while live-tail filtering uses `JsonNode.asText()` ([`LogController.java:120-129`](../server/src/main/java/dev/outpost/query/LogController.java#L120-L129), [`LogController.java:145-173`](../server/src/main/java/dev/outpost/query/LogController.java#L145-L173)). The differential guard uses one 0.1%-selective seeded string attribute and only checks I/O is 4x lower ([`LogQueryPerformanceTest.java:143-159`](../server/src/test/java/dev/outpost/query/LogQueryPerformanceTest.java#L143-L159), [`LogQueryPerformanceTest.java:176-188`](../server/src/test/java/dev/outpost/query/LogQueryPerformanceTest.java#L176-L188)).

- **Explicit risk — the proposed containment rewrite changes equality semantics.** `jsonb_build_object(key, value)` with the HTTP value bound as text searches for JSON string `"3"`. Real SDK attributes preserve types when flattened ([`LogPipeline.java:16-20`](../server/src/main/java/dev/outpost/pipeline/LogPipeline.java#L16-L20), [`LogPipeline.java:70-76`](../server/src/main/java/dev/outpost/pipeline/LogPipeline.java#L70-L76)); the functional test proves numeric `cart.size: 3` currently matches `attr=cart.size=3` ([`LogIngestIntegrationTest.java:78-108`](../server/src/test/java/dev/outpost/ingest/LogIngestIntegrationTest.java#L78-L108), [`LogIngestIntegrationTest.java:185-198`](../server/src/test/java/dev/outpost/ingest/LogIngestIntegrationTest.java#L185-L198)). The seeded acceptance attribute is deliberately stored as text ([`TelemetrySeeder.java:350-371`](../server/src/test/java/dev/outpost/support/TelemetrySeeder.java#L350-L371)), so the suggested rewrite can pass the performance guard while breaking numeric/boolean attributes and making historical queries disagree with live tail.
- **Inferred risk — specialize to the fixture.** The guard neither names `idx_log_attributes` nor varies the key. A one-off expression index or branch for `order.id` can pass while arbitrary dynamic keys remain unindexed.
- **Inferred risk — #128 can invalidate the differential acceptance test.** Today the unfiltered comparator is expensive because it scans and sorts. Once #128 gives the ordinary page an ordered, early-stopping path, a correct selective GIN lookup may no longer be four times cheaper than that already-cheap page (it may need a bitmap scan plus sort). The fixed 4x ratio can then reject a healthy generic attribute plan or reward a fixture-specific combined index.
- **Inferred risk — optimize a request the current UI does not produce.** The logs page parses levels, trace id, and body query, but has no `attr` state/control; attributes are display-only ([`logs.ts:77-99`](../ui/src/app/pages/logs/logs.ts#L77-L99), [`logs.html:115-126`](../ui/src/app/pages/logs/logs.html#L115-L126)). The API feature is real and integration-tested, but ticket priority/benchmark claims should not be presented as current UI impact.
- **Inferred risk — a fast empty result passes.** `EXPLAIN ANALYZE` executes the query, but the performance assertion does not assert match count. The functional suite currently protects one numeric case; it does not cover string, boolean, null, array/object, or parity between stored search and SSE.
- **Acceptance hardening:** define whether `attr=` is textual or typed equality; assert result values and historical/live parity for strings, numbers, booleans, and literal dotted keys; assert the generic GIN index is used for multiple keys; then measure selectivity.

## #133 — trace-search temp spill

Ticket: [Trace search spills ~1.75 GB to temp files on every page](https://github.com/skolldev/outpost/issues/133). Search deduplicates transactions with `DISTINCT ON (trace_id)` ordered by trace id, root preference, and start time before outer keyset pagination ([`TraceController.java:87-150`](../server/src/main/java/dev/outpost/query/TraceController.java#L87-L150)). Acceptance is only that `assertNoTempFiles` hold at benchmark scale; there is intentionally no CI guard because 8,004 transactions fit in memory.

- **Explicit risk — eliminate temp I/O without eliminating the work.** Raising `work_mem` is an explicit option and the ticket itself calls it symptom treatment. It can make `temp=0` while the query still reads and sorts every transaction, remains O(retention), and still takes about two seconds. Under concurrent trace searches it multiplies per-query memory and can trade disk pressure for process/host memory pressure. No logical-I/O or concurrency condition blocks that result.
- **Explicit risk — accept an index that only happens not to spill.** The suggested `(trace_id, parent_span_id, start_ts)` index does not literally match `ORDER BY trace_id, (parent_span_id IS NULL) DESC, start_ts`; the ticket correctly says to verify it is picked. But `temp=0` alone does not prove an ordered index walk or O(page): a smaller/incremental in-memory sort also passes.
- **Inferred risk — benchmark the All-time shape only.** As with logs, the current UI normally sends `from=14d`, while the benchmark calls `/traces` with no range. All time is selectable, so both need measurement rather than substituting one for the other.
- **Explicit risk — an ingest-maintained trace table can break search semantics.** The controller deliberately allows a trace to be found through a matching continuation transaction in another project, then chooses the best matching transaction as representative ([`TraceController.java:87-92`](../server/src/main/java/dev/outpost/query/TraceController.java#L87-L92)); the integration test locks in cross-project continuation discovery ([`TraceQueryIntegrationTest.java:134-160`](../server/src/test/java/dev/outpost/query/TraceQueryIntegrationTest.java#L134-L160)). A simplistic one-row root table is fast but cannot preserve per-transaction project/environment/release/name/duration filters without additional membership/index state.
- **Inferred risk — move an unmeasured cost to transaction ingest and upgrades.** `TransactionStore` is currently append-only batch inserts with no grouping ([`TransactionStore.java:20-24`](../server/src/main/java/dev/outpost/pipeline/TransactionStore.java#L20-L24), [`TransactionStore.java:95-114`](../server/src/main/java/dev/outpost/pipeline/TransactionStore.java#L95-L114)). A trace upsert introduces concurrent hot-row behavior for distributed traces, plus backfill and retention ownership; a new `txn` index adds maintenance to every transaction and a blocking build unless deliberately handled.
- **Inferred risk — no durable regression gate.** The benchmark is opt-in and currently asserts only validity, not temp I/O. Unless acceptance adds an executable assertion to the benchmark, the fix can land with a one-time report and no future protection.
- **Acceptance hardening:** require `temp=0` **and** a structural improvement (ordered index path or trace-table O(page) plan), compare logical I/O/page 1/page 20 at default and All time, exercise both `has_errors` branches, run concurrent searches under a stated memory budget, preserve every search semantic, and measure transaction ingest/backfill/retention costs.

## #106 — log ingest batch unit mismatch

Ticket: [Log ingest collapses past ~40 envelopes/s: max-batch counts items, not records](https://github.com/skolldev/outpost/issues/106). Workers drain at most 500 envelope references, parse all records into one in-memory list, and invoke each signal store once ([`IngestWorkers.java:97-135`](../server/src/main/java/dev/outpost/ingest/IngestWorkers.java#L97-L135), [`IngestWorkers.java:182-207`](../server/src/main/java/dev/outpost/ingest/IngestWorkers.java#L182-L207)). The benchmark always generates 100-record log envelopes and uses fixed 10/20/40/80/160 envelopes/s, 15-second plateaus ([`IngestBenchmark.java:73-100`](../server/src/test/java/dev/outpost/bench/IngestBenchmark.java#L73-L100), [`IngestBenchmark.java:158-165`](../server/src/test/java/dev/outpost/bench/IngestBenchmark.java#L158-L165)).

- **Inferred risk — optimize 100-record envelopes, not bounded work.** A special case, tuned store chunk, or much smaller envelope batch can make those five points monotonic while still allowing one unusually large log item or mixed envelope to create unbounded parse memory/latency. `item_count` is known on the envelope item, but the queue currently owns envelope references, not resumable record chunks.
- **Inferred risk — chunk only inside `LogStore`.** That can bound database transactions, but workers have already parsed and retained up to 50,000 records and do not release any contributing spool until the whole envelope batch finishes. It also does not change `outpost_ingest_store_seconds`: the timer wraps the single outer `logStore.store(logs)` call, so internal chunks are still reported as one long sample ([`IngestWorkers.java:200-207`](../server/src/main/java/dev/outpost/ingest/IngestWorkers.java#L200-L207)).
- **Inferred risk — fix logs by degrading every other signal.** Lowering `max-batch` globally can flatten the log ladder while throwing away error/transaction batching. Acceptance says the unit must mean the same work across signals, but the requested before/after table is log-only and can hide that regression. All three ladders and multi-project behavior should be compared.
- **Explicit/inferred risk — acceptance names a metric the report does not contain.** The ticket requires bounded `outpost_ingest_store_seconds{signal="log"}` p99. Timers publish p99 ([`IngestMetrics.java:113-163`](../server/src/main/java/dev/outpost/ingest/IngestMetrics.java#L113-L163)), but `BenchReport` records HTTP latency, average queue wait, throughput, and allocation—not store-timer percentiles ([`BenchReport.java:34-35`](../server/src/test/java/dev/outpost/bench/BenchReport.java#L34-L35), [`BenchReport.java:84-107`](../server/src/test/java/dev/outpost/bench/BenchReport.java#L84-L107)). A PR can satisfy the table while omitting the second half of acceptance.
- **Inferred risk — read noise as monotonicity.** The benchmark explicitly says throughput is reported, not asserted, because shared-machine thresholds flake ([`IngestBenchmark.java:35-47`](../server/src/test/java/dev/outpost/bench/IngestBenchmark.java#L35-L47)). Requiring every observed step never decrease invites tuning to one five-point run. The structural row-budget invariant should be CI-tested; repeated before/after runs should establish the performance trend.
- **Acceptance hardening:** add a deterministic test that no store call and no retained processed-record collection exceeds a record budget, including one item larger than the budget and mixed signals; expose effective batch units in metrics; report store p99; compare every signal before/after; repeat the log ladder and report variance rather than treating one monotonic sample as proof.

## Recommended review gate for all six

Before implementation, require a one-page “performance contract” answering:

1. What real UI/API request shapes and cardinalities are in scope?
2. What must become asymptotically bounded, rather than merely fit under this fixture's number?
3. What correctness semantics can the optimization accidentally change?
4. What cost moves to ingest, storage, migration/startup, retention, or memory?
5. Which deterministic CI invariant prevents regression, and which opt-in before/after measurements quantify the trade?

The repo's own retracted #129 is the warning: at 40k rows the planner's correct choice looked like a bug, while at 500k the existing trigram index saved 10x ([issue closure comment](https://github.com/skolldev/outpost/issues/129#issuecomment-5152134035), [`measuring-retrieval.md:384-391`](../docs/performance/measuring-retrieval.md#L384-L391)). A performance acceptance test should constrain the structure that matters and separately measure the scale-dependent outcome.
