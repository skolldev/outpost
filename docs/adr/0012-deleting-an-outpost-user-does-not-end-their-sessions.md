# Deleting an Outpost User does not end their Sessions

Outpost authenticates the UI with a stateless server-signed cookie carrying an [[Outpost User]]'s email, role, and expiry, verified by HMAC alone — the filter that populates the security context never reads the database. Deleting an Outpost User therefore removes the account but leaves every [[Session]] already issued to it working until it expires on its own, up to fourteen days later, holding whatever role it was signed with. We accept this rather than make deletion immediate: an [[Installation]] runs on-premises inside the operator's own network, the same boundary that already justifies an open ingest surface and the absence of login rate limiting, and every route to prompt revocation puts a database round trip on the authentication path of every request — the point at which the cookie stops being a cookie and becomes a session record. The same window applies to a password change and would apply to any future role change: neither reaches a Session that is already in someone's browser.

## Considered options

- **A server-side session table.** An opaque cookie identifier against a `session` row, cascading from `app_user`, with the role read live. This is the conventional answer and the only one that makes deletion, password change, and role change all take effect at once; it also yields "sign out everywhere" and a visible list of active Sessions for free. Rejected for now purely on scope — it is the largest change of the three and it sits in the authentication hot path.
- **A `session_epoch` counter on `app_user`,** bumped on deletion and password change and compared against a value carried in the cookie. Cheaper to build, but comparing it requires reading `app_user` on every request, which is the same cost as a session table for strictly less capability. Avoiding that read means an in-memory cache invalidated on write — cleverness with a cache-coherence failure mode, in exchange for saving one primary-key lookup.
- **Shortening the session lifetime, with sliding renewal** so that active users see no login prompt and abandoned Sessions die within a day. This bounds the exposure without a schema change or a per-request read, but it is mitigation rather than revocation: deletion still would not lock anyone out promptly. Rejected to keep this change set out of the session layer entirely.

## Consequences

- **Deletion is an account operation, not an access operation.** The answer to "how do we cut off someone who has left" is "within fourteen days," and it should be given in those words rather than implied to be immediate.
- **Delete-and-recreate does not launder a Session.** Identity in a cookie is the email string, so recreating a deleted address hands the old Session the new account — and because the role travels inside the cookie rather than being read live, the old Session keeps the *old* role. This matters because delete-and-recreate is the sanctioned procedure for both password recovery (ADR-0013) and role change: neither demotes anyone who is already signed in, and neither evicts an attacker from a compromised account.
- **The guard against deleting the last Admin has to be explicit, not inferred.** Refusing self-deletion very nearly implies it, but two Admins each holding a live cookie can delete each other in turn, and `AdminBootstrap` only seeds when the user table is completely empty — so an Installation left with Members and no Admin is unadministrable forever, with no endpoint able to promote anyone. Both guards are therefore enforced, and any future role change must reuse the same last-Admin check.
- **`SessionCookieService`'s "valid across replicas" rationale is doing no work.** ADR-0001 fixes the deployment at one instance; statelessness here buys a saved round trip, not horizontal scale, and that is the trade actually being made.
