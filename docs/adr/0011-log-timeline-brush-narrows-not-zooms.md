# The Log Timeline brush narrows the stream; it does not zoom the chart

The logs page gains a **Log Timeline**: bucketed counts of [[Log Record]]s matching the active filter set, drawn above the stream, split by level. Selecting bars on it filters the stream to that time window. Every comparable product (Splunk, Kibana) treats that selection as a *zoom* — the search window becomes the selection and the chart re-renders spanning only it, re-bucketed finer, with a "zoom out" control to escape. We do the opposite: the chart always spans the **active global range**, and the selection is a sub-window drawn on top of it — selected bars at full height, unselected dimmed. The selection lives in a page-local `window=<fromISO>..<toISO>` query param on `/logs`, which overrides the range-derived `from` and supplies `to` for the list query only. It is never sent to the timeline endpoint, so the chart cannot collapse onto the selection. Any redefinition of the window — global range, Project, [[Environment Name]], or entering live tail — clears it.

Note the name. `shared/sparkline.ts` is the 84×24 non-interactive 14-day issue-row decoration and keeps the word *sparkline*; this is a *timeline*, and the distinguishing property is that it both reads the filters and writes one.

## Considered options

- **Zoom (the Splunk behaviour) vs. overlay.** Zooming means the global range filter — which is relative (`range=1h|24h|7d|14d|30d|all`), lives in `GlobalFilters`, and is carried between pages by `queryParamsHandling: "merge"` — has to start carrying absolute instants, render as "Aug 4 14:12 → 14:47" in the shell's picker, and follow the user onto Issues and Traces. That is a large blast radius bought for a chart gesture. It also discards the surrounding quiet period on every drill, which is most of what makes a timeline diagnostic. Chosen: overlay. An explicit "zoom to selection" action that *promotes* the brush into the global range is the escape hatch for real drill-down and is deferred until usage says it is wanted.
- **`window` as one param vs. `from` + `to`.** Two params would reuse the wire vocabulary `logParams` already serializes, but `from` is also what `GlobalFilters.range` derives, and a URL carrying both an absolute `from` and a relative `range` invites someone to move the brush into the global filter — the thing this ADR exists to prevent. One opaque param makes the ownership legible.
- **Bucket count fixed vs. bucket width fixed.** A fixed bar count (window ÷ 60) keeps chart geometry constant but produces buckets no human can name ("14:07:12 – 14:14:24") and re-slices every record when the window merely slides. Chosen: a ladder of clock-aligned widths (`1m, 5m, 15m, 1h, 2h, 4h, 6h, 1d, 1w`), the smallest rung yielding ≤150 bars, UTC-aligned via `date_bin` to match `IssueController.buildSparklineQuery`.
- **Timeline embedded in the `/logs` response vs. its own endpoint.** Embedding recomputes a full-window aggregate on every "Load more", and dies in live mode where the list resource idles. A separate `GET /logs/timeline` also keeps the aggregate independently `EXPLAIN`-able, which is the precondition for guarding it the way `IssueQueryPerformanceTest` guards the issue sparkline. Chosen: separate endpoint.
- **Live tail.** A moving histogram is where a timeline is most compelling, and the three ways to get one are all bad: freezing it lies, polling puts a recurring full-window aggregate on the largest table per open tab, and incrementing client-side from the SSE stream drifts across the switch-over seam. Chosen: hide the chart while live, and revisit on feedback.

## Consequences

- **The bucket resolution is fixed by the outer range, not by the selection.** Brushing 90 seconds inside a 14-day window filters the stream to 90 seconds while the chart is still drawn in 4-hour bars. This is the accepted cost of not zooming.
- **The timeline is the first query in the logs feature whose cost is O(matching rows) rather than O(page).** `V11`'s indexes bought an ordered walk that stops at 100 rows; an aggregate cannot stop early, and no index removes that. `buildTimelineQuery` is therefore extracted for `QueryPlans`, and `LogTimelinePerformanceTest` guards its block count and partition pruning. Whether `range=all` can be charted within a sane ceiling is a question for that measurement; if it cannot, declining the combination is a separate ADR written against the number.
- **`to` becomes exclusive.** A half-open selection (`from <= t < to`) is required or a record on a bucket boundary is returned by both adjacent selections. `buildLogQuery` currently applies `"timestamp" <= ?`; no caller sends `to` today, so it changes outright.
- **The chart is pointer-only.** No keyboard path to the brush in v1, so its specs assert on the resulting request rather than on chart DOM via `getByRole` as the rest of the suite does.
- **`range=all` gets its left edge from partition metadata** — the lower bound of the oldest surviving `log_record` partition, read from `pg_inherits`. It is filter-blind, so a Project onboarded yesterday shows a long empty runway on All time, and it can precede the first real record by up to a week.
