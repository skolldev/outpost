# The MCP surface is served in-process, and its tools live in the query package

Outpost exposes its telemetry to coding agents and chat assistants through a Model Context Protocol endpoint. Two placements were available: a published client-side package the developer runs locally, which reaches Outpost over HTTP, or an endpoint inside the Spring Boot jar. We chose in-process, served at `/mcp` on the same port as everything else, built on Spring AI's MCP server support. The tools themselves live in `dev.outpost.query` alongside the controllers, not in a feature package of their own.

The placement argument is the one the `Dockerfile` already makes about the Angular bundle: the UI and the server are not independently deployable, and one artifact makes that coupling structural rather than hopeful. A sidecar would be a second release cadence pinned to `/api/internal/**` — a surface deliberately never versioned, because until now its only consumer was compiled into the same jar. It would also carry a third copy of every field name, after the server's record DTOs and `ui/src/app/core/models.ts`. In-process, a [[Tool]] reads through `JdbcClient` directly and returns a payload shaped for a language model rather than for the UI, which is the whole reason the surface is worth having.

The package placement is the less obvious half, and it is a performance decision rather than a taste one. The query statements are not buried inline: each controller exposes `static SearchQuery build…Query(...)` factories returning `(sql, params)`, and the performance guards `EXPLAIN` those factories' output so that a guard cannot keep passing after the real query regresses. Those factories are package-private, and `QueryPlans` records that the boundary was held even for the test harness. Putting the tools in `dev.outpost.query` lets them call the factories without widening it, so every reused query arrives with its guard already written. A separate `dev.outpost.mcp` package would have meant a parallel set of statements with no guards at all — which is issue #126's failure mode, where a green guard asserted the [[Issue]] list was indexed while the Resolved tab cost fifteen times a full table scan, except with the guard removed rather than merely misaimed.

## Considered options

- **A published stdio sidecar (npm).** The universally supported MCP transport, and it could reach the developer's working tree to correlate a stack frame with local source. Rejected: the local-machine advantage is largely spent, because the coding agent calling us already has file and shell tools and only needs the half it cannot get locally — while the costs are permanent. It hard-codes an unversioned internal API, adds a second artifact to release, and the runtime image is distroless with no Node in it, so the sidecar could never ship with the product it belongs to.
- **A separate container or jar from the same codebase.** Keeps MCP concerns out of the main app. Rejected: it adds an operational moving part to a product whose entire pitch is one container and a Postgres, and it buys isolation we do not need at single-instance scale (ADR-0001).
- **A `dev.outpost.mcp` package owning its own SQL.** The conventional feature-package layout, and honest about the tools being a different consumer with differently shaped payloads. Rejected on the guard argument above. The indexes are shared for free because they live in Postgres, but only for queries that keep their shape, and the composites here are shape-specific — `idx_issue_project_status_last_seen_id`, `idx_txn_performance`. Guards are not shared at all.
- **Promoting the `build…Query` factories to a public type.** Would allow a feature package while keeping one copy of each statement. Rejected for now: `QueryPlans` declined to widen that boundary for a benchmark, and a production caller is not a better reason than a test was. Reconsider if a second non-UI consumer appears — a documented public API would be one.
- **Hand-rolling JSON-RPC in a controller.** For a tool-only server this is `initialize`, `tools/list`, `tools/call` and `ping`, and it matches the repo's aversion to dependencies. Rejected as the default but retained as the fallback: an ORM abstracts SQL, which we understand and which does not change, whereas MCP is a specification we do not control. Every other decision on this surface is transport-independent, so reaching for this costs only the transport.

## Consequences

- **The MCP surface version is the server version, structurally.** There is no skew to manage and no upgrade step, and the same argument that forbids a sidecar also forbids ever shipping the tools ahead of the API they read.
- **`dev.outpost.query` grows a second kind of inhabitant.** Controllers serve the UI; tools serve agents; both call the same factories. The package is now organised by what the code queries rather than by who consumes it, which is a deliberate inversion of the usual feature layout and will look wrong to a reader who does not know why.
- **Tool parameters must default to the shapes the indexes were tuned for.** The guards note that every real page load carries a status and a time range because both are defaults a user never picks. An agent will omit both routinely, so the tools apply the same defaults server-side and disclose the window they used. Without that, the reuse buys the SQL but not the plan.
- **Genuinely new composition still needs new guards.** `get_issue_context` joins [[Issue]], [[Event]], [[Log Record]] and [[Span]] in a way no controller does. New statements go through the same `QueryPlans`/`PlanFacts` harness; the reuse rule is not an exemption from guarding.
- **Clients must support remote MCP over HTTP with a bearer header.** Editor clients do. A client that speaks only stdio cannot reach us, and the answer is a shim we would then own, not a change to this decision.
- **Spring AI joins a deliberately short dependency list.** It reached GA in June 2026 against Spring Boot 4. If it fights the hand-rolled `SecurityConfig` filter chain, the fallback above applies.
- **It did not fight the filter chain, and the fallback is not being taken.** `spring-ai-starter-mcp-server-webmvc:2.0.1` on Boot 4.1 registers `/mcp` as a `RouterFunction`, so the chain applies to it by URI like any other path, and the transport's own `JsonMapper` is a named non-default bean — the global `SNAKE_CASE` strategy on the app's mapper never reaches a protocol message. Verified against the MCP Inspector CLI over streamable HTTP with a bearer header.

  Two things had to be pinned rather than defaulted. **The protocol.** The starter's default has been SSE in some versions and streamable in others, and the two mount different paths — `/sse` plus `/mcp/message` against `/mcp` — which is precisely what `SecurityConfig` matches on; a silent default flip would move the endpoint out from under its own authorization rule. **The async dispatch.** Streamable HTTP answers a POST by committing SSE headers and going async, the container re-dispatches, and Spring Security re-authorizes on that dispatch — where `OncePerRequestFilter` does not re-run by default. An empty context there is not a clean 401, because the response is already committed and `sendError` fails: the client sees a torn chunked stream. `ApiTokenFilter` therefore overrides `shouldNotFilterAsyncDispatch`. Anything hand-rolled would have met the same problem, so this is a cost of streaming rather than of Spring AI.
