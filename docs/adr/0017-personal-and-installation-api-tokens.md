# API Tokens are personal or installation-owned, and Members may create personal ones

Until now every [[API Token]] was created by an [[Admin]], owned by nobody, and carried the single scope `artifacts:write`. Exposing telemetry to agents over the [[MCP Surface]] adds the scope `telemetry:read`, and with it the question of who may mint a credential carrying it. We decided that a [[Member]] may create one, and that `api_token` gains a nullable `owner_user_id` referencing `app_user` with `ON DELETE CASCADE`: a token with an owner is a [[Personal Token]] and dies with the account that made it, a token without one is an [[Installation Token]] and outlives everybody. `artifacts:write` remains Admin-only, because uploading [[Artifact Bundle]]s writes to installation resources rather than reading telemetry.

Letting Members mint read tokens grants no capability they lack: a Member can already read every [[Issue]], [[Log Record]] and [[Trace]] in the UI, and the token changes only the transport. What it does change is the durability and revocability of that access. A [[Session]] is short-lived, browser-bound and expires on its own; an API Token is long-lived, sits in plaintext in an editor's configuration file, and until now had nothing tying it to a person. Without an owner, ADR-0012's answer to "how do we cut off someone who has left" — *within fourteen days* — would have quietly become *never*, since an Admin faced with a list of unowned tokens cannot tell which belonged to the departed. The owner column is not bookkeeping; it is the thing that makes the permission safe to grant.

The column is nullable rather than mandatory because ownership and infrastructure pull in opposite directions. A CI token uploading [[Artifact Bundle]]s belongs to the [[Installation]], not to whichever Admin happened to run the setup, and cascading it would mean that offboarding that Admin silently breaks the build. Existing rows migrate to `NULL` and keep working unchanged.

## Considered options

- **Keeping token creation Admin-only.** No migration, no glossary change, no new authorization path. Rejected on friction that scales the wrong way: on a self-hosted installation the Admin is often the same person, and on a team of ten every developer wanting an agent has to queue behind one.
- **An owner on every token, with no null case.** The tidier invariant — every credential traces to a person, and attribution is total. Rejected for the offboarding failure above: it converts deleting an Admin into an unannounced production incident in someone's CI.
- **Deriving ownership from the scope** — `telemetry:read` always personal, `artifacts:write` always installation. Removes a decision from the creation form and matches how the two are actually used. Rejected as a rule that reads as a coincidence: it hard-codes today's scope list into the ownership model and breaks the first time a scope legitimately belongs to both kinds.
- **Requiring an expiry on personal tokens.** The closest analogue to a Session, and it bounds abandonment rather than relying on deletion. Rejected for v1 as a recurring chore for anyone using the MCP surface daily, and because the cascade already covers the case that motivated this. Worth revisiting if abandoned tokens accumulate.
- **A separate credential type for MCP.** Its own table, its own settings page, telemetry-read credentials never mixed with upload credentials. Rejected: `scopes text[]` already expresses the distinction, and a second credential concept would have to be explained in the glossary and the UI forever.

## Consequences

- **Deleting an [[Outpost User]] is now partly an access operation.** ADR-0012 states plainly that deletion is an account operation and that the answer for someone who has left is "within fourteen days". That remains true of Sessions and is now false of Personal Tokens, which stop working immediately. The asymmetry is deliberate — a cascade on a table we already read per request costs nothing, whereas revoking a Session means a database round trip on the authentication path of every request — but it must be stated in both halves rather than implied to be uniform.
- **The token list has to show ownership.** "Personal to alex@example.com" and "Installation" are different objects with different lifetimes, and a list that renders them identically invites an Admin to revoke the wrong one. Admins see and may revoke all tokens; a Member sees and manages only their own.
- **Scope selection becomes part of the creation form.** `TokenController.create` currently hardcodes `List.of(SCOPE_ARTIFACTS_WRITE)`. It must accept scopes and reject any that the requesting role may not grant, which is the first place authority over scopes is enforced rather than assumed.
- **The settings page copy stops being about CI.** It currently describes tokens as being for uploads from CI. That framing is now half the story.
- **Delete-and-recreate does not launder a token the way it launders a Session.** ADR-0012 notes that recreating a deleted address hands the old cookie to the new account, because identity in the cookie is the email string. Tokens reference `app_user.id`, so a recreated account is a different owner and the old tokens are already gone.
