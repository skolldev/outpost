# Transaction Group statistics are computed live, over a window capped at 30 days

[[Transaction Group]] statistics — p50/p95/p99, count, total time, avg, max — are computed by aggregating `txn` at query time, with no rollup table and no materialized view, following the precedent `LogController.buildTimelineQuery` set for the Log Timeline. Percentiles come from a single `percentile_cont(ARRAY[…]) WITHIN GROUP (ORDER BY duration_ms)` so one sort serves all four. The window is capped at **30 days**: `GlobalFilters` offers `range=all`, which yields no `from` and therefore no `start_ts` predicate, and an aggregate with no `start_ts` predicate reads every weekly partition of `txn` that has ever existed and sorts every duration in it. The server clamps and echoes the window it actually used; the UI shows the cap rather than letting the filter claim something the numbers do not support.

The trade-off worth remembering is that **exact percentiles foreclose pre-aggregation**. `count`, `sum`, `min`, `max` and `avg` are mergeable — hourly rollups combine into a 30-day answer — but percentiles are not, because a p95 of p95s is not a p95. Choosing exact percentiles is choosing to always scan raw rows. If volume ever makes that untenable, the escape is not a rollup of these statistics but a redesign onto duration histograms, whose buckets *are* mergeable and from which percentiles can be derived approximately.

## Considered options

- **min/avg/max only, no percentiles.** Streaming aggregates, no sort, trivially cheap, and mergeable — a rollup table stays open as an option indefinitely. Rejected because it does not do the job: latency distributions are long-tailed, so an average of 90 ms comfortably hides 5% of Transactions at 3 s, and a max is a single unstable outlier. The feature exists to find tail latency.
- **Duration histograms.** Streaming, mergeable, survive a future rollup, and render a distribution that exposes bimodality — the honest long-term answer. Deferred, not rejected: it is meaningfully more to build and gives approximate percentiles, and the installation sizes Outpost targets do not yet need it.
- **Honouring `range=all`.** Consistent with every other page and gives a true lifetime view. Rejected against the measurement discipline in `docs/performance/measuring-retrieval.md`: it defeats partition pruning and spills the sort to temp files, two of the four facts `PlanFacts` exists to assert on.
- **Clamping silently.** Simplest, needs no new UI affordance. Rejected — the numbers would quietly disagree with the filter the user can see, which is the failure mode that produces "the numbers are wrong" bug reports.

## Consequences

- **The list is top-N, not keyset-paginated.** Every other list surface in Outpost pages through `KeysetPage`; this one cannot, because an aggregate does not exist until every row in the window has been read, so there is no key to seek on. The endpoint returns at most 100 groups plus a `truncated` flag and no cursor, and the way to see past it is to filter, not to page. This divergence is deliberate and carries a comment at the call site.
- **This is the second query in the codebase whose cost is O(matching rows) rather than O(page)**, after the Log Timeline. It needs its own guard alongside `LogTimelinePerformanceTest`, reaching the controller's own SQL through `QueryPlans` — and the sort makes temp-file blocks the fact to watch, where the timeline's concern was block count.
- **The global range filter means something different on this page.** `all` is unavailable and 30d is the ceiling. The alternative was a wart discovered in production rather than in the picker.
- **Data retention silently truncates the window.** An installation retaining 7 days shows 7 days of data under a 30-day range with nothing on screen saying so. Left open deliberately; it applies to every page, and fixing it here alone would be inconsistent.
